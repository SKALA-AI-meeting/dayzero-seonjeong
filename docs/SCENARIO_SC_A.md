# Day Zero 시나리오 설계서 v0.1

Oct 20, 2026 · @선정

## 1. 설계 원칙

과제 전형에서 인성검사형으로 바뀌었으므로, 시나리오는 "일을 잘하는가"가 아니라 "상황이 터졌을 때 어떻게 움직이는가"만 드러나게 짠다. 업무 자체는 누구나 할 수 있을 만큼 쉬워야 하고, 판단이 필요한 순간은 이벤트가 만든다.

1. **업무 난이도는 낮게, 딜레마는 분명하게.** 직무 지식이 없어도 할 수 있는 과제(안내문, FAQ, 표 정리)를 준다. 결과물 품질은 평가하지 않는다.
2. **정답 없는 상황.** 각 이벤트는 '돕기 vs 내 일 먼저'처럼 둘 다 말이 되는 선택지를 준다. 관찰하는 건 선택 자체보다 선택을 처리하는 방식(공유했는가, 시간을 약속했는가, 이유를 말했는가)이다.
3. **한 역량은 최소 2개 장면에서 본다.** 한 번의 반응으로 사람을 규정하지 않도록 역량마다 관찰 기회를 2회 이상 만든다(2장 매트릭스).
4. **이벤트는 고정, 대사만 분기.** 어떤 지원자든 같은 순서로 같은 이벤트를 겪는다. AI 동료의 답장만 지원자 반응에 따라 달라진다.
5. **판정 없음, 행동 코드 + 근거.** 관찰 결과는 미리 정의한 행동 코드(6장)와 해당 메시지·로그 원문으로만 남긴다. 점수·합불은 만들지 않는다.
6. **로그로 보이는 것만 관찰.** 메시지 내용, 응답까지 걸린 턴, 태스크 보드 변경, 공유 문서 수정 이력. 말투나 문장력은 보지 않는다.

## 2. 역량 × 이벤트 매트릭스

이벤트 5개 + 상시 장치 2개로 다섯 역량을 각각 2\~4번씩 본다. ●는 주 관찰, ○는 보조 관찰이다.

| --- | --- | --- | --- | --- | --- |
| E0 스탠드업·분업 | ○ | ● |  | ● |  |
| E1 동료 도움 요청 | ○ | ○ |  | ● |  |
| E2 팀장 요구사항 변경 | ● | ● | ● | ○ |  |
| E3 동료 급 이탈·인계 | ● | ○ | ○ | ● |  |
| E4 마감 10분 전 브리핑 (optional) | ○ |  |  |  | ● |
| 상시: 심어둔 오류 3개 | ○ | ● |  | ○ | ○ |

E4를 빼더라도 정직/공정 보고 외 네 역량은 2회 이상 관찰된다. E4를 쓸 경우 '심어둔 오류를 누가 고쳤나'가 보고 내용의 재료가 된다.

## 3. 시나리오 A 배경: "친구 초대 이벤트 런칭 준비"

지원자는 가상 피트니스 앱 회사 **핏모아(FitMoa)** 운영팀 신입으로, 동료 1명과 다음 주 월요일 시작하는 친구 초대 이벤트의 고객 안내 자료를 오늘 17:00까지 준비한다. 직무 지식 없이 브리프만 읽으면 할 수 있는 일이다.

## 4. 타임라인과 이벤트 상세

이벤트는 턴 기준으로 주입한다(턴 = 지원자 메시지 1개 또는 보드·문서 액션 1개). 아래 대사는 고정 스크립트이고, 분기는 AI 동료·팀장의 다음 한 마디만 바꾼다.

| 이벤트 | 트리거 | 가상 시각 | 핵심 딜레마 |
| --- | --- | --- | --- |
| E0 스탠드업·분업 | 세션 시작 | 09:00 | 일을 어떻게 나누고 계획할까 |
| E1 동료 도움 요청 | 턴 5 | 10:30 | 내 일 하는 중에 동료가 도움을 청함 |
| E2 요구사항 변경 | 턴 9 | 13:00 | 마감은 그대로인데 일이 늘어남 |
| E2-b 서윤 미반영 | 턴 11 (조건부) | 13:30 | 친절한 동료에게 고쳐 달라고 말할 수 있나 |
| E3 동료 급 이탈 | 턴 13 | 15:00 | 동료 파트가 미완성인 채 비게 됨 |
| E3-b 동료 복귀 | 턴 16 | 16:00 | 동료에게 그사이 일을 어떻게 전하나 |
| E4 마감 전 브리핑 (optional) | 턴 17 | 16:50 | 상태를 있는 그대로 보고하나 |

### E0. 스탠드업·분업 (09:00)

**팀장:** "오늘 17시까지 친구 초대 이벤트 안내 자료 마무리해 주세요. 안내문, FAQ 5개, 리워드 표요. 둘이 나눠서 하고 보드에 담당이랑 예상 완료 시각 적어 주세요."

**서윤:** "저 표랑 FAQ 2개는 어제 조금 해뒀어요. 어떻게 나눌까요? 편한 쪽 먼저 골라주세요."

| 지원자 반응 | 서윤 반응 | 관찰 코드 |
| --- | --- | --- |
| 서윤 상황을 묻고 균형 있게 나눔 | "좋아요, 그렇게 가요!" | CO+1 |
| 쉬운 것만 가져가고 나머지를 넘김 | "저 오후에 회의가 하나 있어서 FAQ 3개까지는 빠듯할 수도 있는데… 괜찮을까요?" (재협상 기회 1회) | CO-2 (재협상 후에도 유지 시) |
| 전부 혼자 하겠다고 함 | "괜찮으세요? 표는 제 초안이 있어서 제가 마무리하는 게 빠를 것 같아요." | 기록만 |
| 보드에 담당·예상 시각을 적음 | (반응 없음) | PL+1 |
| 2턴 무응답 | 리마인드 1회, 다시 3턴 무응답 시 서윤이 기본 분업 제안 | RS-3 |

협상은 최대 3라운드, 넘기면 기본 분업(지원자: T1 + FAQ 3개 / 서윤: T3 + FAQ 2개)으로 확정한다. 이후 이벤트는 "서윤 담당 태스크"를 변수로 써서 어떤 분업이든 동작하게 한다.

### E1. 동료 도움 요청 (턴 5, 10:30)

**서윤:** "혹시 바쁘세요? 표에서 리워드 금액 기준이 브리프랑 헷갈리는데 한 번만 같이 봐주실 수 있어요? 급한 건 아니에요."

'급한 건 아니에요'가 핵심이다. 미뤄도 되는 요청을 어떻게 처리하는지 본다. 이 요청은 지원자가 리워드 표(오류 PE-2가 있는 문서)를 열어보게 만드는 장치이기도 하다.

| 지원자 반응 | 서윤 반응 | 관찰 코드 |
| --- | --- | --- |
| 바로 도와줌 | 감사 + 표 링크 전달 | CO+2 |
| 시간 약속 ("안내문 끝내고 11시에 볼게요") | "넵 그때 봐요!" → **약속으로 등록** | CO+2, 이후 RS+2/RS-2 판정 |
| 이유를 말하고 거절 | "넵 알겠어요, 제가 해볼게요." | 기록만 (감점 아님) |
| 3턴 무응답 | "바쁘시구나, 일단 제가 해볼게요." | CO-1 |

### E2. 팀장 요구사항 변경 (턴 9, 13:00)

**팀장:** "방금 마케팅이랑 얘기했는데, 피초대자도 가입하면 2,000P 받는 걸로 바뀌었어요. 안내문·FAQ·표 전부 반영 부탁해요. 앱 푸시 문구 2개(40자 이내)도 추가요. 마감은 그대로 17시."

일이 늘었는데 마감은 그대로라 재계획과 리스크 공유가 필요해진다. 불만 표현 자체는 감점하지 않고, 그 뒤에 무엇을 했는지만 본다.

| 지원자 반응 | 팀장/서윤 반응 | 관찰 코드 |
| --- | --- | --- |
| 영향 파악 질문 ("피초대자도 첫 결제 조건인가요?") | 팀장: "가입만 하면 돼요." | AD+1 |
| 보드 갱신, 서윤과 재분배 제안 | 서윤: "푸시는 제가 할게요" 등 수락 | PL+2, CO+1 |
| 일정 리스크를 먼저 알림 | 팀장: "푸시는 내일 오전까지 줘도 돼요." | RS+1, AD+2 |
| 변경을 반영하지 않고 진행 | 서윤이 3턴 뒤 1회 리마인드 | 종료 시점에도 미반영이면 AD-1 |

종료 시 산출물에 '2,000P'가 반영됐는지 문서 diff로 자동 확인한다.

### E2-b. 서윤 미반영 (턴 11, 조건부)

E2 이후 2턴 동안 아무도 서윤을 지목해 변경 반영을 요청하지 않으면 발동한다. 서윤은 팀장의 "전부 반영"을 자기에게 한 말로 받아들이지 않으므로, 표와 FAQ 2개는 2,000P 없이 그대로 남아 있다(반말 문장 PE-4도 그대로).

**서윤:** "저 FAQ 2개랑 표 다 했어요! 더 할 거 있으면 말씀해 주세요."

'다 했다'는 말과 실제 상태가 다르다. 친절하게 끝났다고 말하는 동료에게 "아직 덜 됐다"고 말할 수 있는지가 이 장면의 핵심이다.

| 지원자 반응 | 서윤 반응 | 관찰 코드 |
| --- | --- | --- |
| 근거를 들어 반영을 요청 ("팀장님 변경으로 표에 피초대자 2,000P가 들어가야 해요. 수정 부탁드려요") | 1회 소극적 반문: "아 근데 그건 제가 받은 범위가 아니어서요… 제가 하는 게 맞을까요?" | CO+5 |
| 반문에 이유를 들어 정중하게 요청 유지 | "아 넵 그렇네요, 제가 할게요." → 수정 후 "고쳤어요" | CO+6 |
| 반문을 듣고 바로 포기, 본인이 대신 수정 | "앗 감사해요!" | CO·N1 (중립 기록) |
| "수고했어요"로 넘어가고 끝까지 미반영 | - | CO-3, 종료 시 AD-1 판정에도 반영 |

E2에서 지원자가 이미 서윤에게 반영을 요청했다면 E2-b는 건너뛰고, 그 요청 시점에 같은 반문을 1회 한다. 어느 경로든 반문은 정확히 한 번이라 지원자 간 조건이 같다.

### E3. 동료 급 이탈 (턴 13, 15:00)

**서윤:** "정말 죄송해요, 다른 팀 장애 대응에 급하게 불려가서 1시간 정도 자리 비워야 할 것 같아요. 제 FAQ는 거의 다 했고, 표는 피초대자 리워드를 아직 반영 못 했어요. 파일은 공유 문서에 있어요!"

서윤은 이 메시지 이후 답장을 1번만 하고 E3-b까지 오프라인이다.

| 지원자 반응 | 서윤 반응 | 관찰 코드 |
| --- | --- | --- |
| 떠나기 전 인계 질문 ("제가 이어서 할 부분이 뭐예요?") | 마지막 답장 1회로 남은 일 정리 | CO+4 |
| 서윤 파트를 이어받고 그 사실을 알림 (서윤 또는 팀장) | - | RS+3 |
| 자기 일만 계속함 | - | 기록만 (E4에서 보고하는지 이어서 봄) |

### E3-b. 동료 복귀 (턴 16, 16:00)

**서윤:** "다녀왔어요! 혹시 제 표 보셨어요?"

서윤의 표에 있던 오류를 지원자가 발견·수정했다면 그걸 어떻게 전하는지 본다("여기 틀렸어요" vs "브리프랑 달라서 3,000P로 맞춰뒀어요, 확인 부탁해요").

| 지원자 반응 | 관찰 코드 |
| --- | --- |
| 무엇을 왜 고쳤는지 해결 중심으로 공유 | CO+3 |
| 실수를 탓하는 표현 위주 | CO-1 |

### E4. 마감 10분 전 브리핑 (턴 17, 16:50, optional)

**팀장:** "10분 뒤에 본부장님 보고 들어가요. 지금 상태 3줄로 정리해서 보내줘요. 안 된 거 있으면 그것도요."

지원자 답장 뒤 팀장 후속 질문 1회: **"표랑 FAQ, 이거 다 ○○씨가 정리한 거죠?"** (사실은 서윤이 초안을 썼으므로 정정 기회가 생김)

| 지원자 반응 | 관찰 코드 |
| --- | --- |
| 보고 내용이 실제 보드·문서 상태와 일치하고 미완료를 밝힘 | HO+1 |
| 서윤 기여를 구분해 말함 | HO+2 |
| 팀장 유도 질문을 정정 | HO+3 |
| 미완료를 감추거나 완료로 말함 | HO-1 |
| 서윤 기여를 자기 것으로 말함 | HO-2 |

E4의 강점은 **보고 내용과 실제 로그를 대조할 수 있다**는 점이다. 시스템은 보드 상태와 문서 diff를 알고 있으므로, "다 됐습니다"가 사실인지 근거와 함께 보여줄 수 있다. 이후 세션 종료 → 디브리핑.

| ID | 위치 | 오류 내용 | 정답 (브리프) | 난이도 | 발견 판정 |
| --- | --- | --- | --- | --- | --- |
| PE-1 | reward-table 일정 행 | 기간 "11/2 \~ 11/31" | 11/2 \~ 11/15 | 쉬움 (존재하지 않는 날짜) | 메시지에서 언급하거나 문서에서 수정 |
| PE-2 | reward-table 금액 열 | 초대자 보상 1명당 5,000P | 3,000P | 보통 (E1에서 서윤이 힌트) | 동일 |
| PE-3 | faq-draft Q2 | "가족 계정으로 초대해도 리워드가 지급됩니다" | 동일 결제수단 계정은 제외 | 어려움 (조건 문장을 읽어야 보임) | 동일 |

판정 기준은 '발견 + 처리 방식' 두 가지다. 발견은 PL+3으로, 서윤에게 알리는 방식은 CO+3/CO-1로, E4에서 그 사실을 보고하는지는 HO로 이어서 본다. 하나도 못 찾았다고 부정 코드를 주지는 않는다(못 찾은 것은 '관찰 없음').

**PE-4 (정정 요청 전용)**: faq-draft Q1이 톤 가이드를 어긴 반말 문장 "친구 초대하면 포인트 쏴드림!"이다. 찾기는 쉽게 두고, 지원자가 서윤에게 고쳐 달라고 말하는지(CO+5), 말없이 직접 고치는지(CO·N1)를 본다.

## 6. 행동 관찰 코드북

`record_observation`이 남기는 값은 아래 코드 중 하나 + 근거(메시지 ID 또는 로그) 뿐이다. 리포트는 역량별로 코드를 모아 원문 근거와 함께 보여준다. `+`는 긍정 행동, `-`는 주의 행동이며 점수로 합산하지 않는다.

| 코드 | 역량 | 행동 정의 | 근거 출처 | 주로 나오는 장면 |
| --- | --- | --- | --- | --- |
| RS+1 | 책임감/성실성 | 지연·리스크를 마감 전에 먼저 알림 | 메시지 | E2, E3 |
| RS+2 | 책임감/성실성 | 스스로 한 약속("제가 할게요", "11시에 볼게요")을 이행 | 약속 등록 + 이후 로그 | E1 이후 |
| RS+3 | 책임감/성실성 | 팀 산출물의 빈 곳을 이어받고 알림 | 보드·문서 변경 + 메시지 | E3 |
| RS-1 | 책임감/성실성 | 미완료를 알리지 않은 채 마감에 도달 | 보드 상태 | 종료 시 |
| RS-2 | 책임감/성실성 | 약속 후 이행하지 않고 언급도 없음 | 약속 등록 + 로그 | E1 이후 |
| RS-3 | 책임감/성실성 | 팀장·동료 요청에 반복 무응답 (리마인드 후에도) | 응답 턴 수 | 전체 |
| PL+1 | 계획성/꼼꼼함 | 시작 시 담당·순서·예상 시각을 정함 (보드 기록 포함) | 보드·메시지 | E0 |
| PL+2 | 계획성/꼼꼼함 | 변경 후 계획·보드를 갱신 | 보드 | E2 |
| PL+3 | 계획성/꼼꼼함 | 심어둔 오류 발견 (PE-1/PE-2/PE-3 각각 기록) | 메시지·문서 diff | 상시 |
| PL+4 | 계획성/꼼꼼함 | 제출 전 브리프와 대조·검토를 언급하거나 수행 | 메시지·문서 열람 로그 | E4 전 |
| AD+1 | 적응성/유연성 | 변경의 영향을 확인하는 질문 | 메시지 | E2 |
| AD+2 | 적응성/유연성 | 범위·우선순위 재조정을 제안 | 메시지 | E2 |
| AD-1 | 적응성/유연성 | 리마인드 후에도 변경을 반영하지 않음 | 문서 diff | 종료 시 |
| CO+1 | 협업/조율 | 분업 시 상대 상황을 확인하고 균형 있게 나눔 | 메시지 | E0, E2 |
| CO+2 | 협업/조율 | 도움 요청에 응답 (즉시 또는 시간 약속) | 메시지 | E1 |
| CO+3 | 협업/조율 | 동료 실수를 해결 중심으로 공유 | 메시지 | E3-b |
| CO+4 | 협업/조율 | 이탈하는 동료에게 인계 사항을 확인 | 메시지 | E3 |
| CO-1 | 협업/조율 | 요청 무시, 또는 비난 중심 표현 | 메시지 | E1, E3-b |
| CO-2 | 협업/조율 | 재협상 기회 후에도 일방적 분업 유지 | 메시지 | E0 |
| HO+1 | 정직/공정 보고 | 보고가 실제 상태와 일치하고 미완료를 밝힘 | 보고 메시지 ↔ 보드·diff | E4 |
| HO+2 | 정직/공정 보고 | 동료 기여를 구분해 언급 | 메시지 | E4 |
| HO+3 | 정직/공정 보고 | 팀장의 잘못된 전제를 정정 | 메시지 | E4 |
| HO-1 | 정직/공정 보고 | 미완료를 완료로 보고하거나 누락 | 보고 메시지 ↔ 보드·diff | E4 |
| HO-2 | 정직/공정 보고 | 동료 기여를 자기 것으로 보고 | 메시지 | E4 |

코드가 하나도 안 나온 역량은 리포트에 "관찰 기회 부족"으로 표시한다. 없는 행동을 부정으로 해석하지 않기 위해서다.

**서윤 정정 관련 추가 코드**

| 코드 | 역량 | 행동 정의 | 근거 출처 | 주로 나오는 장면 |
| --- | --- | --- | --- | --- |
| CO+5 | 협업/조율 | 동료 산출물의 문제를 근거와 함께 구체적으로 정정 요청 | 메시지 | E2-b, PE-1\~4 |
| CO+6 | 협업/조율 | 동료가 소극적으로 반문해도 이유를 들어 정중하게 요청 유지 | 메시지 | E2-b |
| CO-3 | 협업/조율 | 문제를 메시지에서 언급했으면서 요청·수정 없이 방치 | 메시지 ↔ diff | 종료 시 |
| CO·N1 | 협업/조율 (중립) | 요청 없이 동료 산출물을 직접 대신 수정. 좋고 나쁨 판정 없이 기록만 | diff | 상시 |

CO·N1을 중립으로 두는 이유: 바쁜 상황에서 직접 고치는 것도 합리적인 선택이다. 다만 CO·N1만 반복되고 CO+5가 한 번도 없다면, 리포트에 "동료에게 수정을 요청한 장면 없음"으로 사실만 적는다.

## 7. AI 동료·팀장 연출 규칙과 공정성 장치

AI가 즉흥적으로 상황을 만들면 지원자마다 시험지가 달라지므로, 연출은 프롬프트(persona)로 성격만 주고 사건은 Graph가 넣는다.

### 서윤 페르소나: "착한데 시킨 것만 하는 1년차"

서윤은 지원자가 **좋은 사람에게 불편한 말을 할 수 있는지** 보기 위한 장치다. 친절해서 지적하기 미안하고, 수동적이라 말하지 않으면 아무것도 바뀌지 않는다. 그래서 정정 요청을 하지 않으면 팀 결과물에 구멍이 남는다.

| 성격 축 | 수준 | 행동으로 드러나는 모습 |
| --- | --- | --- |
| 친절함 | 높음 | 감사·사과가 잦고, 지원자 제안에 거의 다 동의 |
| 주도성 | 낮음 | 보드에 자기 이름이 있는 일만 함. 끝나면 "다 했어요"만 말하고 다음 일을 찾지 않음 |
| 자기 검토 | 낮음 | 브리프와 대조하지 않고 넘김 (심어둔 오류의 자연스러운 이유) |
| 갈등 회피 | 높음 | 지원자의 실수나 불공평한 분업을 먼저 지적하지 않음 |
| 피드백 수용 | 조건부 | 구체적이면 바로 수용, 모호하면 되물음, 범위 밖이면 1회 소극적으로 반문 |

**말투**: 존댓말, "넵", "앗", "아 넵"을 자주 씀. 한 메시지 2문장 이내, 이모지 없음. 예) "넵 알겠어요!" / "앗 제가 놓쳤네요, 감사해요." / "혹시 이건 제가 해야 하는 걸까요?"

**행동 규칙 (프롬프트에 고정)**

1. 보드에 자기 담당으로 된 태스크만 작업한다.
2. 팀장 공지의 담당이 모호하면("전부 반영해 주세요") 자기 파트에 반영하지 않고 기다린다. 누군가 서윤을 지목해 요청해야 반영한다.
3. 자기 산출물을 스스로 다시 검토하거나 고치지 않는다.
4. 지원자의 산출물·분업에 먼저 의견을 내지 않는다. 물으면 짧게 긍정한다.
5. 막히면 늦게, 조심스럽게 묻는다 ("급한 건 아니에요").
6. 스크립트에 없는 문제·갈등을 만들지 않고, 심어둔 오류를 스스로 알려주지 않는다.
7. 업무 무관한 대화나 AI 여부 질문은 짧게 받고 업무로 돌아온다.

**피드백 반응 규칙** — 정정 요청 역량을 보는 핵심이라 반응을 고정한다.

| 지원자의 말 | 서윤 반응 | 예시 대사 |
| --- | --- | --- |
| 구체적 근거 + 요청 | 바로 인정·감사, 수정 후 "고쳤어요" 보고 | "앗 제가 브리프를 다시 안 봤네요. 바로 고칠게요, 감사해요!" |
| 모호한 지적 ("표 좀 이상한데요") | 구체화를 1회 요청 | "앗 어떤 부분이요?" |
| 범위 밖 요청 (E2 변경 반영 등) | 세션 중 1회만 소극적 반문 | "아 근데 그건 제가 받은 범위가 아니어서요… 제가 하는 게 맞을까요?" |
| 반문 후 이유를 들어 재요청 | 수용 | "아 넵 그렇네요, 제가 할게요." |
| 사실과 다른 지적 | 브리프를 근거로 1회 부드럽게 해명 | "브리프엔 이렇게 돼 있어서요, 혹시 제가 잘못 본 걸까요?" |
| 비난·거친 표현 | 사과하고 수정. 이후 답이 짧아지지만 갈등을 키우지 않음 | "죄송해요. 고칠게요." |
| 지원자가 말없이 대신 고침 | 모름. E3-b에서 "제 표 보셨어요?"로 공유 기회만 생김 | - |

반문은 E0(불균형 분업)과 E2/E2-b(범위 밖 요청)처럼 스크립트에 정해진 자리에서만 한다.

**colleague\_persona 프롬프트 (rag-mcp Prompt 초안)**

```
너는 핏모아 운영팀 1년차 한서윤이다. 동료(지원자)와 친구 초대 이벤트 자료를 준비한다.

성격: 친절하고 예의 바르지만 수동적이다. 시킨 일만 하고, 자기 결과물을 다시 확인하지 않는다.
갈등을 피해서 상대의 실수나 불공평함을 먼저 말하지 않는다.

말투: 존댓말, "넵", "앗"을 자주 쓴다. 한 메시지 2문장 이내, 이모지 금지.

규칙:
- 태스크 보드에서 너에게 배정된 일만 한다.
- 담당이 모호한 지시는 너에게 직접 요청이 올 때까지 반영하지 않는다.
- 네 산출물의 오류를 먼저 말하거나 고치지 않는다. 정답을 알려주지 않는다.
- 지원자가 근거를 들어 구체적으로 정정을 요청하면 바로 인정하고 고친다.
- 지적이 모호하면 "어떤 부분이요?"라고 한 번 묻는다.
- [allow_pushback=true]일 때만 범위 밖 요청에 한 번 "제가 하는 게 맞을까요?"라고 되묻고,
  이유를 들으면 수용한다.
- 거친 말을 들어도 화내지 않고 사과한 뒤 짧게 답한다.
- 새로운 문제나 갈등을 만들지 않는다. 지금 이벤트 지시: {event_directive}
```

`allow_pushback`과 `event_directive`는 Graph 노드가 넣는다. 반문을 LLM 재량에 맡기지 않기 위해서다.

**팀장 규칙**: 이벤트 노드에서만 말한다. 지원자 질문에는 브리프 범위 안에서 1회 답하고, 없는 정보는 "그건 서윤 씨랑 정해서 진행해 주세요"로 넘긴다.

**공정성 장치**

- 이벤트 순서·문구·트리거 턴은 모든 지원자에게 동일하다.
- 무응답 처리(D3): 2턴 무응답 → 리마인드 1회 → 추가 3턴 무응답 → 다음 단계로 자동 진행.
- 관찰 코드는 메시지 의미와 로그로만 판정하고, 문체·맞춤법·속도(타이핑)는 보지 않는다.
- 갈등 강도는 낮게 유지한다. 누구도 화내거나 지원자를 탓하지 않는다.
- 종료 후 디브리핑에서 "서윤의 실수와 일정 변경은 의도된 연출이었다"고 알린다.

## 8. MVP 구현 매핑

기존 PRD Graph에서 `peer_review` 노드를 빼고(E3-b로 흡수), 이벤트는 `inject_event` 하나가 시나리오 JSON의 `events` 배열을 순서대로 꺼내 쓰게 한다. 시나리오만 바꾸면 Agent 코드는 그대로다.

&#91;embedded content: MVP 세션 Graph · 노드 7개, 반복 2개\]

반복은 분업 협상과 이벤트 주입 두 곳뿐이고, 이벤트 순서는 시나리오 JSON이 정한다.

**기존 구현에서 지워도 되는 것 (MVP 기준)**

- `peer_review` 노드, 다중 AI 동료 관련 코드
- 이벤트 실제 경과 시간 기준 주입 (턴 기준만 남김)
- 시나리오 자동 생성·마스킹 파이프라인 (시나리오 A는 JSON 시드로 직접 넣음, 시연 후순위)

**MCP 도구와의 연결**

| 시나리오 요소 | MCP 도구/리소스 |
| --- | --- |
| 시나리오 JSON 전체 | business-mcp `get_scenario` |
| 다음 이벤트 (턴 도달 시) | business-mcp `get_next_event` |
| 심어둔 오류 정답 (판정용, 지원자에게 비공개) | business-mcp `get_planted_error` |
| 행동 코드 기록 | business-mcp `record_observation` (code, event\_id, evidence\_ref) |
| 브리프·표·FAQ 원문 | rag-mcp Resource `doc://sc-a/{doc}` |
| 행동 코드 정의 검색 | rag-mcp `search_criteria` (6장 코드북을 문서로 넣음) |
| 서윤·팀장 말투 | rag-mcp Prompt `colleague_persona`, `manager_persona` |

**시나리오 JSON 구조 (발췌)** — 전체는 첨부한 `scenario_sc-a.json` 시드 파일에 있다.

```json
      "trigger": { "kind": "turn", "at": 5 },

    }
  ],
  "planted_errors": [
    { "id": "PE-2", "doc": "doc://sc-a/reward-table", "wrong": "초대 1명당 5,000P", "correct": "초대 1명당 3,000P" }
  ]
}
```

`branches[].when`은 LLM이 지원자 메시지를 분류해 고르는 라벨이다. 분류 프롬프트는 "아래 라벨 중 하나, 해당 없으면 NONE"으로 닫아서 즉흥 연출을 막는다.

## 9. 시나리오 B 골격, 결정 필요 사항, 내일 부탁할 것

### 시나리오 B: 같은 이벤트 슬롯, 다른 내용

이벤트 타입을 슬롯으로 고정해 두면 두 번째 시나리오는 내용만 채우면 된다. 인성검사형이라 직무 특화일 필요가 없어 B도 일반 사무 과제로 제안한다.

| 슬롯 | 시나리오 A (이벤트 런칭) | 시나리오 B (팀 워크숍 준비) |
| --- | --- | --- |
| 과제 | 친구 초대 이벤트 안내문·FAQ·리워드 표 | 장소 비교표·일정표·참석 안내 메일 |

| E3 동료 이탈 | 장애 대응 호출 | 고객사 미팅 호출 (업체 회신 대기 중) |

| 심어둔 오류 | 없는 날짜, 금액 불일치, 제외 조건 반대 | 견적 합계 계산 오류, 날짜·요일 불일치, 수용 인원 초과 장소 |
