# 고도화 로드맵 — 기업별 맞춤 시험 시나리오 생성 (P1 이후)

작성: 2026-10-20 · 상태: **제안 (미구현)** · 관련: PRD §7 P1 "다중 시나리오, 기업 커스터마이징"

## 1. 왜 필요한가

현재 MVP는 시나리오 1개(`moarun-rejoin-v1`, 루프랩 모아런 재참여율 개선)로 동작한다. 하지만 이 서비스를 여러 회사에 판매하려면 각 회사가 **보고 싶은 역량과 직무 상황**에 맞는 시험을 받아야 한다. 예를 들면 다음과 같다.

- 핀테크 A사: "규제 제약 속에서 우선순위를 정하고, 법무팀과 이견을 조율하는 기획자"
- 커머스 B사: "데이터로 문제를 정의하고, 개발 일정 변경에 유연하게 대응하는 PM"

따라서 **회사 요구사항을 입력받아 → 그 회사에 맞는 시나리오(회사 자료·이벤트·동료 행동·관찰 항목)를 만들고 → 검증해 배포하는 기능**이 필요하다.

## 2. 지금 무엇이 이미 준비되어 있고, 무엇이 막혀 있나

코드를 실제로 점검한 결과다(2026-10-20 15:2x).

시나리오와 결합된 참조는 코드 29개 파일에 있다(테스트 스크립트 포함). **핵심 결론은 "데이터는 이미 분리됐고, 행동 규칙이 코드에 묶여 있다"이다.** 고도화의 1단계는 이 행동 규칙을 선언형 시나리오 스펙으로 옮기는 일이다.

## 3. 목표 기능 흐름

```text
[기업 담당자]                         [Day Zero]                                  [검수자(사람)]
 ① 요구사항 입력  ───────────▶  ② 시나리오 초안 생성(LLM + 템플릿)  ───────▶  ③ 검토·수정
   - 직무/연차                      - 가상 회사·서비스·인물                       - 사실 일관성
   - 보고 싶은 역량(최대 5)          - 회사 자료 N개 + 수치 데이터셋                - 공정성·난이도
   - 업무 맥락/금지 소재             - 과제 브리프·제출물 섹션                       - 법적·윤리 검토
   - 시험 시간                       - 이벤트 타임라인(역량별 관찰 상황)
                                     - 동료 행동 규칙·설계 오류
                                     - 관찰 항목·리포트 매핑
                                            │
                                 ④ 자동 검증(시뮬레이션) ◀────────────────────────┘
                                   - 수치 검산, 자료 간 모순 검사
                                   - 가상 지원자 경로 A/B/C로 이벤트·리포트 재현
                                            │
                                 ⑤ 버전 고정·배포 → 초대 생성 시 시나리오 선택
```

### ① 기업 입력 (최소 항목)

| 항목 | 예시 | 용도 |
|---|---|---|
| 직무·연차 | 서비스 기획 2~4년차 | 과제 난이도, 동료 수준 |
| 관찰하고 싶은 역량 | 책임감, 존중·소통, 협력, 유연성, AI 활용, (+ 기업 정의 역량) | 이벤트 설계와 리포트 영역 |
| 업무 도메인·상황 | B2B SaaS 온보딩 개선 | 가상 회사·데이터 생성 |
| 반드시 넣을/뺄 소재 | 실제 사명·고객사 금지, 규제 상황 포함 | 생성 가드레일 |
| 시험 시간·제출물 형식 | 90분, 1~2쪽 | 타임라인 길이 |

실제 회사 데이터는 받지 않는 것을 기본으로 한다. 가상 회사로 재구성해 정보 유출과 공정성 문제를 막는다.

### ② 시나리오 스펙 (선언형) — 현재 `data/{id}/`를 확장

```yaml
id: fintech-limit-v1
company: {name: 가상사명, service: ..., people: [manager, colleague]}
deliverable: {sections: [{id, title, default_owner}], pages: "1~2"}
documents: [{id, title, body, release_at_min}]          # 기존과 동일
datasets:                                              # 도메인 도구를 범용화
  - id: funnel
    schema: {dimensions: [segment, channel], measures: [users, converted]}
    rate: converted / users
events:
  - id: help_request
    at_min: 30
    competency: COLLABORATION
    kind: COLLEAGUE_HELP_REQUEST            # 엔진이 아는 이벤트 유형(템플릿)
    message: "…"
    observe: ["응답했는가", "대안을 제시했는가"]
  - id: designed_error
    at_min: 70
    kind: COLLEAGUE_POLICY_CONFLICT
    conflicts_with: {document: policy, quote: "…"}   # 정정 판단 근거를 데이터로
colleague: {persona, can_do, cannot_do, triggers: {recheck_on: [...]}}
report: {areas: [{id, label, events: [...]}]}
```

핵심은 **이벤트 "유형" 라이브러리**다. 분담 제안, 도움 요청, 자료 지연, 요구사항 변경, 동료 설계 오류, 마감 보고는 엔진 코드로 한 번 구현한다. 시나리오는 유형·시각·문구·근거만 지정한다. 지금 `timeline.py`/`graph.py`의 이벤트 ID별 분기를 이 유형 기반으로 옮기면 된다.

### ③·④ 품질 장치 (판매 신뢰성의 핵심)

- **사실 일관성 자동 검사**: 데이터셋 합계 검산(현재 AT-02 방식), 문서 간 수치 대조, 설계 오류가 실제 정책 문장과 충돌하는지 확인
- **시뮬레이션 리허설**: 가상 지원자 스크립트(현재 `smoke_flow`)를 시나리오마다 자동 생성해 모든 이벤트·리포트 영역이 재현되는지 확인
- **공정성**: 같은 시나리오 버전에서는 모든 지원자에게 같은 이벤트 시각·조건 적용(현재 원칙 유지). 시나리오별 난이도 지표(자료 분량, 이벤트 밀도) 기록
- **사람 검수 필수**: LLM이 만든 시나리오는 검수자 승인 전 배포 불가. 승인 이력을 남기고 버전을 고정(`scenario_version`)
- **금지 사항**: 실존 기업·인물·고객 데이터 사용, 점수·합불 생성, 민감 특성(성별·나이 등)과 관련된 상황 설계

### ⑤ 관리자 기능

- 시나리오 목록·버전·상태(초안/검수 중/배포)
- 초대 생성 시 시나리오 선택
- 기업별 리포트 영역 이름 커스터마이징(평가 로직 자체는 공통)

## 4. 단계별 계획

| 단계 | 내용 | 산출물 | 대략 규모 |
|---|---|---|---|
| P1-a 엔진 범용화 | 이벤트 유형 라이브러리화, 섹션·단서·화면 문구를 시나리오 스펙에서 읽기, 프롬프트 템플릿화(회사명·인물 변수), 범용 데이터셋 조회 도구 1개로 통합 | 두 번째 시나리오를 **코드 수정 없이** 데이터만으로 추가 가능 | 2~3주 |
| P1-b 수작업 시나리오 2~3개 | 직무·도메인이 다른 시나리오를 사람이 작성해 엔진 검증 | 시나리오 라이브러리 v1 | 1~2주 |
| P2-a 생성 보조 | 기업 입력 폼 → LLM이 스펙 초안 생성 → 자동 검증 → 검수 화면 | 시나리오 생성기 | 3~4주 |
| P2-b 운영 | 시나리오 버전 관리, 기업별 대시보드, 시나리오별 리포트 비교 | 다기업 운영 | 2~3주 |

권장 순서는 **P1-a → P1-b → P2-a**다. 생성기를 먼저 만들면, 엔진이 특정 시나리오에 묶여 있는 한 생성된 시나리오를 실행할 수 없다.

## 5. 이번 MVP에서 미리 지켜 둔 것 (이후 작업을 쉽게 하는 설계)

- 시나리오 데이터·문서·이벤트 시각·고정 메시지를 `data/{scenario_id}/`와 seed로 분리
- 모든 세션이 `scenario_id`·`scenario_version`·`policy_version`을 기록하므로 리포트 재현 가능
- Agent·MCP·Harness·승인·리포트 틀은 시나리오와 무관하게 동작
- 벡터 색인이 `scenario_id`·`index_version`으로 구분됨

## 6. 열린 질문 (사업·운영 결정 필요)

1. 기업이 직접 시나리오를 만들게 할지, Day Zero 운영팀이 대행할지(검수 책임 주체)
2. 기업 정의 역량을 허용할 범위. 공통 5영역 외 추가 시 관찰 근거 설계 기준
3. 시나리오 간 결과 비교를 허용할지. 난이도가 달라 직접 비교는 위험하다
4. 채용 활용 시 법적 검토(설명 의무, 데이터 보관 기간, 자동화된 의사결정 규제)
